# Гипотезы и проверка корпуса — этап 8

Гипотеза, наблюдение и результат исполнения правил — разные сущности. Гипотезу
формулирует инженер; поле с понятным именем или Passed не доказывает его назначение.
Карточка содержит statement, rationale, scope, observation_ids, unknowns и contradictions.
Уточнение создаёт immutable версию с parent_id и общим hypothesis_id. Ссылки ведут к
постоянным наблюдениям с исходными stream/source anchors; наблюдения не переписываются.

## Корпус и зафиксированные входы

`CorpusSpec` содержит **явный список capture_ids** (без скрытого «все записи проекта»),
direction (`both`, `a_to_b`, `b_to_a`), IPv4 address, port, start_ns/end_ns.
Адрес/порт совпадают с любой стороной соединения; время — пересечение с интервалом
сессии, включая границы. При заданном времени сессия без подходящей временной метки
исключается. Unix nanoseconds сохраняются как точные строки. A/B не объявляют роли устройств.

Версия корпуса неизменяема, хранит имя, спецификацию, SHA-256, parent_id и corpus_id.
Повторное сохранение того же содержимого в этой истории возвращает прежнюю версию.
Добавление новой записи в проект не меняет старый явный состав: её включают в новую версию.

Перед запуском читается согласованный metadata snapshot через PostgreSQL REPEATABLE READ:

- версия и SHA модели, точный JSON, конфигурация framing;
- версия корпуса, capture IDs/hashes, packet counts, import engine/settings/checksum policy и диагностика;
- reconstruction ID/hash/version/settings, directed streams, policy, extent, inclusion и source-status counts;
- `reconstruction_failures`: соединение, направление, причина ошибки и включение фильтрами для каждого невосстановленного направления;
- версии движков framing, interpretation и validation, project/run IDs, время запуска.

Криптографическая проверка оригиналов и reconstruction artifacts выполняется в процессе
до/после исполнения и перед публикацией. Изменение входного восстановления во время работы
завершает задачу ошибкой, не выдавая частичный запуск за завершённый. Новая immutable версия
модели/корпуса не меняет выбранную старую версию; завершённый запуск может сразу стать историческим.

## Выполнение и покрытие

Один и тот же `frame` и Construct-backed `parse_message` применяются ко всем включённым
направлениям. Не нужны отдельные настройки полей для каждого сообщения. Framing внутри
validation не зависит от выбранного в UI preview: используется конфигурация **версии модели**.
В каждой строке сообщения сохранена воспроизводимая framing identity и source anchor.

| Статус | Значение в проверке корпуса |
| --- | --- |
| passed | Сообщение потреблено целиком, заданные проверки выполнены, байты однозначны |
| failed | Нарушено правило/константа/диапазон/длина; ранее прочитанные поля сохраняются |
| unknown | Недостаточные данные, неописанный вариант/хвост, неразмеченные bytes или ошибка framing |
| ambiguous | Конфликтующие исходные байты; ни один вариант не объявлен фактом |
| not_applicable | Направление исключено фильтрами, нет application bytes, либо известные non-TCP данные вне области |

Неопределённость данных имеет приоритет над Passed/Failed, а конкретная диагностика
проверки остаётся видна. Неразмеченные остатки **внутри выбранного корпуса** — Unknown,
или Ambiguous при конфликте. Отдельный preview этапа 7 помечает их Not applicable к
field parser; корпусный результат дополнительно учитывает непокрытые данные выбранной области.

Неудачный framing одного потока не блокирует остальные: весь его extent получает Unknown
с причиной. Превышение локального decode limit даёт Unknown соответствующего диапазона.
Сбой источника, отмена или общий защитный предел не публикуют завершённый запуск.

Сводка включает:

- пять статусов по всем единицам результата и отдельно по **сообщениям**;
- byte_counts, в сумме равные extent всех восстановленных направлений выбранных capture IDs;
- selected/excluded stream bytes; unframed bytes; undecoded included bytes; decoded int/bytes leaf bytes;
- отсутствующие/усечённые и конфликтующие source bytes включённых направлений;
- все выбранные captures и packets, noneligible packets и captures_without_reconstruction.
- `unreconstructed_directions` и `excluded_unreconstructed_directions`: число ошибочных направлений внутри и вне фильтров корпуса.

Container-поля array/switch не прибавляют перекрывающиеся байты повторно. Поле, не прошедшее
проверку константы, всё равно сохраняет прочитанное значение и source range.
Пустые направления имеют собственные stream IDs и диагностические строки, без выдуманного
непустого anchor. Для записи без reconstruction существует Unknown-строка, её extent неизвестен:
процент полного покрытия не заявляется. Unsupported/malformed capture conditions остаются
в source snapshot и отдельной диагностике; хороший TCP-обмен той же записи остаётся доступным.
Фильтр списка результатов в UI **не меняет** корпус и полную сводку.

Ошибка восстановления направления сохраняется отдельной строкой
`kind=reconstruction_diagnostic` с `session_id`, `direction` и исходной причиной.
Включённое направление получает Unknown; исключённое фильтрами получает Not applicable.
`stream_id` и `anchor` равны null: размер потока неизвестен и не добавляется в byte_counts.
GUI позволяет открыть соединение и его диагностику. Эти же строки, счётчики и снимки
создаёт CLI; публикация отклоняет результат с пропущенной диагностикой направления.

## История, актуальность и сравнение

Каждый успешный запуск сохраняется как immutable JSONL + PostgreSQL indexes. Новый запуск
получает новый UUID; одинаковые входы дают те же значения, statuses и source ranges, а не
переписывают старый результат. Parent model/corpus IDs и старые source hashes остаются доступны.

`currentness` сообщает timestamp проверки, latest model/corpus version IDs, причины и детали:
новая сохранённая версия в той же истории, новый engine version, изменённое/недоступное
восстановление или source. Актуальность определяется относительно **последней сохранённой**
версии каждой истории; намеренный повтор со старой версией остаётся историческим.
Ошибка проверки актуальности не показывается как подтверждение актуальных входов.
В UI несохранённые условия и текущий выбор, отличающийся от snapshot, отмечены отдельно.

Сравнение сопоставляет `(capture_id, stream_id, reconstruction_version, start, end, kind)`.
Для диагностики без потока дополнительно используются `session_id` и `direction`,
чтобы разные ошибки не сливались при сравнении.
Смена границ/координат не угадывает соответствие: появляются added/removed ranges.
Совпавшие диапазоны сравниваются по status, извлечённым полям/значениям/anchors и диагностике.
Первым показывается изменение статуса; остальные факты доступны в деталях обоих результатов.
Сводка различий считается целиком, страницы содержат до 100 строк. Same sources означает
одинаковые **capture IDs/hashes**; разные условия корпуса отражаются отдельными диапазонами.

## API

Все пути имеют префикс `/api/v1`; list endpoints используют offset/limit (1..1000).

- `POST/GET /projects/{id}/hypotheses`; `GET /hypotheses/{id}` и `/hypotheses/{id}/evidence`.
- `POST/GET /projects/{id}/corpora`; `GET /corpus-versions/{id}`.
- `POST /projects/{id}/validation-runs`: `{corpus_version_id,interpretation_version_id}` → JobSnapshot, 202.
- `GET /projects/{id}/validation-runs`: лёгкие summary, без огромных source snapshots.
- `GET /validation-runs/{id}`: immutable snapshot и coverage.
- `GET /validation-runs/{id}/currentness`: проверка актуальности и деталей источника.
- `GET /validation-runs/{id}/results?status=failed`: paginated summary, без поля payload/full fields.
- `GET /validation-runs/{id}/results/{result_id}`: значения и anchors одной строки.
- `GET /validation-runs/{id}/compare/{other_id}`: сводка и страница различий.

Модель, корпус, evidence и сравниваемые запуски должны принадлежать одному проекту.
Публикация проверяет identity, полное nonoverlapping coverage каждого stream, обязательные
capture diagnostics, filtered scope и framing/source anchors. Ошибка откатывает DB-транзакцию.
Навигация от поля использует прежние bounded bytes/source endpoints, а не копию всего PCAP в JSON.

Задача `corpus_validation` выполняется локально, поддерживает SSE и отмену. Прогресс измеряет
две проходные позиции extent (framing/decoding) и одну единицу на capture; это не размер PCAP.
Сохраняющая фаза committing не отменяется. Registry не переживает рестарт, результаты — переживают.

## Ограничения реализации

До 1000 capture IDs и 10000 directed streams в snapshot; до 500000 строк результата и
512 МиБ JSONL. Пределы сообщений/полей берутся из модели этапов 6–7. Hypothesis evidence —
до 128 observations; основные текстовые поля/пункты — до 10000 символов.
Проверка пишется потоково по одному диапазону, DB inserts — пакетами; сравнение проходит
по sorted summaries, а не загружает все fields. Эти пределы защитные, не формат протокола.
Linux workload/timings/peak RSS будут проверены на этапе 10.
Миграция `0006_validation` добавляет четыре таблицы и не меняет прежнее evidence.
Текущая версия движка — `validation-v2`: старые запуски `validation-v1` сохраняются
и помечаются устаревшими. Новые поля JSON имеют совместимые значения по умолчанию;
исторические снимки и архивы остаются читаемыми. Изменений SQL-схемы для этой коррекции нет.
Перенос, отчёт и CLI остаются для этапа 9. PPP/MPTCP/IPv6/AI/live capture не добавлялись.
