# Ручное ревью этапа 6

Настройте `.env` и PostgreSQL по [инструкции запуска](manual-stage-5.md#запуск).
API и Alembic автоматически читают `.env`, `source` не нужен. Из корня проекта:

```sh
uv sync --project backend --frozen
docker compose up -d
uv run --project backend --frozen alembic -c backend/alembic.ini upgrade head
uv run --project backend --frozen uvicorn protocol_lab.api.app:app --host 127.0.0.1 --port 8000
```

Во втором терминале:

```sh
cd frontend
npm ci
npm run dev
```

Откройте http://127.0.0.1:5173. Новая миграция — 0004_framing, добавляет таблицы
и сохраняет данные предыдущих этапов. Для каждой записи ниже: импортировать,
«Восстановить TCP», выбрать соединение и A→B. Блок фрейминга находится под HEX.

1. **Фиксированный размер.** `tests/fixtures/tcp/ordered.pcap`, поток HELLOWORLD.
   В блоке фрейминга выберите фиксированный режим, начало=0, размер=5.
   «Построить предварительный просмотр»: 2 сообщения, 0 неразмеченных позиций.
   Нажмите строку [0,5): HEX выделит HELLO; исходник — пакет #3.
   Сообщения в одном TCP-пакете остаются отдельными.
2. **Сообщение через пакеты.** `tests/fixtures/tcp/reordered-retransmitted.pcap`.
   Размер=7: сообщение HELLOWO [0,7), остаток RLD [7,10).
   В источниках сообщения должны быть пакеты разных частей и повторные передачи.
3. **Устойчивое наблюдение.** Сохраните наблюдение для [2,7). Измените размер 7→5
   и постройте снова. Новый run ID, 2 сообщения. Прежний результат выбирается в
   «Сохранённый результат фрейминга»; наблюдение остаётся на [2,7), с tcp-v1 и теми
   же источниками. Изменение формы до построения не меняет показанный результат.
4. **Ручные границы.** ordered.pcap: режим «Ручные границы», строки `0:3` и `5:10`.
   Получите 2 сообщения и остаток [3,5). Можно выделить bytes в HEX и нажать
   «Добавить выделение как сообщение». Перекрытие диапазонов должно дать понятную ошибку.
5. **Поле длины.** `tests/fixtures/framing/length-big.pcap`: начало=0, смещение поля=0,
   ширина=2, Big endian, множитель=1, поправка=2. Получите 3 сообщения:
   [0,5), [5,12), [12,15). Поле длины первого сообщения разделено между TCP-пакетами.
   `length-little.pcap` с Little endian даёт те же границы.
6. **Не хватает данных.** `length-incomplete.pcap` с настройками пункта 5:
   одно сообщение [0,5), остаток [5,8), диагностика incomplete_length_message.
   Неустановленные границы не должны показываться как успешно выделенные сообщения.
7. **Маркеры.** `tests/fixtures/framing/markers.pcap`: start `AA BB`, end `CC DD`.
   Два сообщения [5,12) и [12,21); остатки [0,5) и [21,25), всего 9 позиций.
   Маркеры включены в диапазоны. Поиск проходит через TCP packet boundaries.
8. **Неопределённые bytes.** `tests/fixtures/tcp/gaps-overlaps.pcap`, размер=5:
   сообщение [0,5) с конфликтом, [5,10) с пропуском, остаток [10,13) с усечением.
   «Границы по правилу» не означает известный payload; статусы данных видны отдельно.
9. **Сохранение и отмена.** Перезагрузите страницу/перезапустите API. Выберите поток
   и сохранённую версию: диапазоны и наблюдения остаются. На большом потоке можно
   отменить running/queued задачу; маленькие записи часто завершаются до нажатия.
   Для проверяемой отмены очереди и ошибки protective limits есть integration tests.

Фильтр сообщений/остатков работает среди загруженных диапазонов; при необходимости
нажимайте «Загрузить ещё». Сводка охватывает весь поток. Правило — гипотеза границ;
разбор полей, редактор протокольной модели и corpus validation пока не реализованы.
PPP/MPTCP-поддержка не добавлена на этом этапе; файл iperf-mptcp-0-0.pcap из обсуждения
остаётся unsupported_linktype. Для ревью используйте перечисленные синтетические записи.
