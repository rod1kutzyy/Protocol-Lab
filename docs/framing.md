# Фрейминг: границы сообщений, этап 6

Фрейминг преобразует один directed stream в полный упорядоченный набор диапазонов:
`message` и `leftover`. Их непересекающееся объединение покрывает **весь extent**, включая
пропуски, усечения и конфликтующие bytes. Это исполнение заданного правила границ,
а не доказательство семантики протокола и не декодирование полей (этап 7).

Ядро `framing/engine.py` не зависит от HTTP/SQLAlchemy. Адаптер читает известные bytes
из immutable capture по карте TCP provenance, порциями ≤65536. Для результата
сохраняются capture ID/SHA-256, stream ID, reconstruction version, engine version
`framing-v2`, настройки schema `framing-1`, counts и все диапазоны.

## Правила

Общий `start` — абсолютный offset начала автоматического фрейминга. Префикс до него
остаётся `leftover`. Ручная разметка использует абсолютные диапазоны и start=0.
Границы и смещения всегда `[start,end)`.

- `manual`: упорядоченные непустые диапазоны без перекрытий. Разметка явно обозначена
  как гипотеза инженера. Промежутки и хвост остаются неразмеченными.
- `fixed`: положительный полный размер сообщения. Отсчёт ведётся от `start` независимо
  от TCP packet boundaries. Неполный хвост — leftover. Известное выравнивание по правилу
  не скрывает missing/ambiguous payload внутри сообщения.
- `length`: unsigned поле ширины 1/2/4/8, offset от начала сообщения, big/little endian.
  `total = raw_value × multiplier + adjustment`. Полный total включает все header bytes;
  total должен быть положительным, в пределах лимита и не короче конца поля длины.
  Пример: uint16 payload length в [0,2), multiplier=1, adjustment=2.
  Неизвестное/конфликтующее поле, недопустимая длина или неполный хвост оставляет
  оставшийся диапазон с диагностикой. Автоматическое новое выравнивание не угадывается.
- `markers`: явно заданные start/end HEX, по 1–64 bytes. Сообщение включает оба маркера;
  первый end после полного start завершает его. Escaping/вложенность не предполагаются.
  Маркеры ищутся только внутри непрерывных известных участков, включая границы пакетов
  и страниц чтения. Unknown/ambiguous разрывает поиск; сообщение через такой барьер
  не объявляется известным. Следующий известный start может начать новый поиск.
  Если end не найден до конца известного участка/лимита, остаток этого участка не
  размечается, с диагностикой; скрытого выбора другого конца нет.

`boundary_status=known` у message означает границы по выбранному правилу, а не
доказанную границу реального протокола. У leftovers — `uncertain`.
`data_status`: known / incomplete (gap или truncated) / ambiguous / mixed.
`uncertain_bytes` — суммарная длина диапазонов с data_status != known, включая их
известную часть; это не число потерянных bytes. В UI название раскрывает эту область.

## Версии, источники и наблюдения

Идентичные source/version/spec дают один content-addressed run ID и те же piece IDs.
Изменение правил создаёт новую версию; прежняя остаётся доступной. Каждый piece
имеет framing_version=run ID и anchor к исходному stream/reconstruction version/range.
Переход к его bytes использует прежний GET stream bytes, с точным clipping источников,
включая все retransmissions и конфликтующие варианты.

Наблюдения и ручные action links не ссылаются на mutable message ID. Они сохраняют
свои прежние stream/source anchors при любом повторном фрейминге. Originals,
TCP artifacts и manifest не переписываются. Миграция 0004 только добавляет таблицы
`framing_runs` и `framing_pieces`.

## API

Все пути имеют префикс `/api/v1`.

| Маршрут | Результат |
| --- | --- |
| POST streams/{id}/framing | FramingSpec → 202 JobSnapshot kind=stream_framing |
| GET streams/{id}/framing | Сохранённые версии; offset/limit |
| GET framing-runs/{id} | Settings, source/version, extent и counts; pieces читаются отдельно |
| GET framing-runs/{id}/pieces | Полные anchors/statuses/diagnostics, offset/limit |

limit до 1000, UI запрашивает 100 и виртуализирует загруженные строки.
Фильтр UI «Сообщения/Остатки» применяется только к явно указанному набору загруженных
диапазонов; сводка всегда охватывает весь поток. Загрузить ещё не скрывает остатки.

Защитные пределы: max_message_bytes по умолчанию 1 MiB, настраивается до 16 MiB;
max_pieces по умолчанию 200000; manual до 10000 ranges. Это ограничения ресурсов,
а не предполагаемые пределы протокола. При превышении max_pieces — failed job,
без публикации частичного результата. Для marker end за max_message_bytes диапазон
остаётся leftover с диагностикой. Формулы ограничены integer multiplier/adjustment;
произвольные expressions/code не выполняются.

Операция выполняется локальным процессом с прогрессом и отменой. До `committing`
отмена не публикует результат и очищает staging; во время транзакции отмена закрыта.
Успешный предварительный просмотр сохраняется неизменяемо; прежние версии доступны
после failed/cancelled и после рестарта API. Сам реестр jobs не переживает рестарт.

## Уточнение диагностик A0

`framing-v2` различает отсутствие end marker до конца потока, неизвестные bytes
и технический предел поиска. Length-rule отдельно сообщает превышение
`max_message_bytes`. Необязательное `technical_limit` содержит точные observed/maximum
и признак нижней границы, если полный размер неизвестен. Это не нарушение протокола;
остаток не скрывается. Исторические `framing-v1` остаются читаемыми, их IDs/диагностика
не меняются. [Полные контракты A0](inference-a0.md).
