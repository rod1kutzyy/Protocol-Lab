# Восстановление TCP — этап 4

Реализована часть R1: экземпляры соединений, два направления, sequence-aware
восстановление и точное происхождение диапазонов. Ядро `tcp/reassembly.py`
не импортирует HTTP или PostgreSQL. Прикладные сообщения здесь не выделяются:
один payload может содержать несколько сообщений, одно сообщение — несколько payload.

## Версия и идентичность

Версия движка `tcp-v1`, политика `retain-all-overlaps`. Session UUID вычисляется
из capture UUID, версии и индекса первого отнесенного к соединению пакета.
Stream UUID добавляет направление `a_to_b` или `b_to_a`. Повторное исполнение с
теми же входами и настройками возвращает те же идентификаторы и результат.

Новый исходящий SYN с новым ISN выделяет новый экземпляр соединения, даже если
закрытие прежнего не попало в запись; прежний конец обозначается недоступным.
Одинаковые SYN не создают дополнительных сессий. RST либо FIN с обеих сторон
обозначает закрытие; финальный ACK не создает новую сессию. Запоздалый payload
в уже известном диапазоне до FIN сохраняется в прежней сессии с явной
`post_close_payload_identity_uncertain`, а не создает ложное новое соединение. Это учет границ
соединения, а не восстановление полного автомата TCP.

При недоступном начальном SYN первая наблюдаемая сторона становится A;
`start_known=false`, `roles_known=false`. Повторное использование tuple без SYN
или закрытия невозможно доказать только по наблюдаемым данным: это явно отмечено
`connection_identity_uncertain_without_syn`. Достоверные роли устанавливаются
по начальному SYN, но simultaneous open оставляет роли неопределенными.
Поздно записанный исходный SYN после SYN-ACK учитывается без перестановки байтов.

PCAPNG section/interface образуют отдельные области наблюдения. Между ними
соединения автоматически не объединяются; API показывает section_index/interface_id
и `cross_observation_domain_identity_unknown`, если присутствует несколько областей.
Одно физическое соединение, записанное на нескольких интерфейсах, поэтому может
появиться несколько раз: связь между областями остается неизвестной.

## Sequence numbers и интервалы

Все интервалы полуоткрытые `[start,end)`. SYN занимает sequence position, но не
байт приложения. Payload SYN начинается с `seq+1`. FIN также занимает sequence
position, но не входит в extent потока. ACK-only пакеты не добавляют данные или
пустые диапазоны. Sequence numbers разворачиваются относительно ближайшей
наблюдаемой позиции в полупространстве 32-битного счетчика. Расстояние ровно
2^31 или extent >=2^31 считается неоднозначным и получает диагностику вместо
предположенного порядка. Больше одного полного оборота без промежуточного
наблюдаемого трафика доказать невозможно.

При наличии SYN origin — первый application sequence number; иначе origin —
минимальная наблюдаемая позиция payload. Это не утверждение, что ранее байтов
не было. Пропуски перед первым доступным payload без SYN неизвестны и не получают
выдуманной длины. Gap между известными позициями отражается явно.

Восстановленный поток состоит из spans:

- `known`: один наблюдаемый вариант; одинаковые retransmissions не удваивают bytes,
  но каждая исходная передача остается в provenance.
- `ambiguous`: разные наблюдаемые варианты на одинаковых sequence positions.
  Все источники сохранены, победитель не выбирается.
- `gap`: позиции между доступными данными без наблюдаемых bytes.
- `truncated`: IPv4/TCP объявляет payload, часть которого не захвачена.
  Поздняя полная retransmission может покрыть этот диапазон.

Checksum policy наследуется от capture. `warn` сохраняет payload даже с плохой
checksum; `reject` исключает его из восстановления, сохраняя исходник и индекс.
Неподдерживаемые/неполные заголовки остаются в packet index. Excluded packet IDs
записаны в артефакте восстановления. Ethernet и IPv4 декодируются только до
поддерживаемых заголовков, без рекурсивного обхода неизвестных вложенных протоколов.

Ошибку sequence/защитного лимита одного направления видно в session diagnostics;
это направление не выдается как успешно восстановленное, другое направление и
остальные сессии остаются доступны. Ошибка целостности источника или глобального
лимита сессий завершает job с failed и сохраняет ранее опубликованные данные.

## Происхождение и API

`POST /api/v1/captures/{id}/reconstruct` с `{}` создает `tcp_reconstruction` job.
Состояния, SSE и отмена общие с импортом. `queued/running` можно отменить;
`committing` закрывает отмену. Публикация происходит в одной DB-транзакции.

`GET /captures/{id}/sessions?offset=0&limit=100` возвращает список метаданных,
`next_offset`, packet_count и направления без списков всех packet IDs и spans.
`GET /sessions/{id}` и `GET /streams/{id}` возвращают метаданные.
До первого успешно опубликованного результата sessions возвращает 409.

`GET /streams/{id}/bytes?offset=0&length=64` возвращает только выбранные позиции:
blocks со статусами и variants (`data_hex`, sources). У gap/truncated variants
пусты. В каждом источнике сохранены:

- capture_id, packet_id, packet_index;
- packet_payload_range относительно TCP payload;
- packet_offset относительно начала captured frame;
- file_offset относительно начала исходного PCAP/PCAPNG;
- stream_id, reconstruction_version и соответствующий stream range.

Края запрошенного диапазона обрезают provenance точно на те же байты.
`GET /packets/{packet_id}` позволяет открыть сетевые заголовки исходного пакета.
Все варианты конфликта сохраняют свои источники. Список sources при одинаковых
bytes содержит все retransmissions.

Защитные пределы: максимум 10000 сессий, 1000000 spans на направление,
256 МиБ сравниваемых bytes при overlaps. Они сохраняются в результате и задаются
в теле reconstruct. Запрос bytes: length 1..65536, диапазон внутри extent,
до 10000 источников и 4 МиБ чтения payload для вариантов за один ответ;
превышение возвращает 422 без тихого обрезания. Это лимиты ресурсов, не формат
исследуемого протокола. Первое чтение проверяет SHA-256 исходника; повторные чтения используют stat-кэш
(inode/size/mtime_ns/ctime_ns), изменение которого вызывает повторную проверку.
Проверка выполняется в фоновом
потоке API: на больших файлах проверка имеет стоимость полного чтения источника.

## Хранение и наблюдения

Добавляющая миграция `0002_tcp_reconstruction` создает reconstructions,
tcp_sessions, tcp_streams, tcp_spans, observations. Нужен явный `alembic upgrade head`.
Существующие проекты и исходники не изменяются. Manifest v1 с bootstrap revision
0001 остается совместимым; текущая DB revision хранится Alembic.

Артефакт `derived/<reconstruction_uuid>-<sha256>.json` содержит версию, настройки,
сессии, spans и все source mappings. Bytes не дублируются: API читает их из
immutable original по source offsets. SQL содержит индекс диапазонов и метаданные.
Артефакт сохраняется без перезаписи, с SHA-256 и относительным путем. При откате
может остаться проверяемый orphan, повторная публикация может его переиспользовать.
Полный перенос с DB snapshot остается этапом 9.

Сохраненный `tcp-v1` результат неизменяем. Повтор с теми же настройками идемпотентен;
попытка сохранить отличающийся результат для той же версии возвращает failed.
Изменение алгоритма требует новой версии. Изменение защитных настроек после первой
публикации не заменяет существующий результат.

`POST /projects/{id}/observations` принимает text и anchors со stream_id,
reconstruction_version и byte_range. API проверяет проект, версию и границы,
сам создает SourceRange для доступных bytes всех вариантов. Gap можно наблюдать
по stream anchor без выдуманного источника. Наблюдение не зависит от message_id
и не перемещается при будущей смене framing. `GET /projects/{id}/observations`
возвращает сохраненные наблюдения с пагинацией. UI редактора — последующие этапы.
